# 🔁 FCM 알림 처리 시스템 개선 - Redis Streams 도입기

## 📌 개요

기존 알림 발송 시스템은 단일 쓰레드 또는 선형 처리 방식으로 구성되어 있어, 트래픽 급증 시 병목과 누락이 발생할 수 있었습니다.  
이를 개선하고 **안정적이고 유실 없는 메시지 처리 구조**를 만들기 위해 **Redis Streams 기반의 이벤트 스트리밍 아키텍처**를 도입했습니다.

---

## 1. ❓ 왜 도입했는가?

기존 구조는 다음과 같은 한계를 가지고 있었습니다:

- 트래픽 급증 시 **단일 소비 처리 병목**
- 장애 발생 시 메시지 **재처리 불가**, 유실 위험 존재
- 병렬 확장성 부족 → 시스템 탄력성 저하
- 모니터링 및 운영 추적 어려움

---

## 2. 🧠 왜 Redis Streams인가?

| 기술 | 장단점 | 비고 |
|------|--------|------|
| ✅ Redis Streams | ✅ 병렬 소비 가능, ✅ 메시지 추적, ✅ Group 기반 ack 처리, ✅ DLQ 연동 가능 | ✔️ 도입 |
| RabbitMQ | ✅ 성능 우수, ❌ 구조 복잡, ❌ Redis 연동 어려움 | 대체 가능 |
| Kafka | ✅ 대규모 처리에 적합, ❌ 오버스펙, ❌ 운영 복잡 | ❌ 미도입 |
| RDB Polling | ❌ 유실 추적 어려움, ❌ 성능 낮음 | ❌ 제한적 |

Redis Streams는 Redis 기반으로 가볍고 빠르며, `XREADGROUP`, `XACK`, `XPENDING`, `XCLAIM` 등 메시지 처리 제어 기능이 뛰어나  
**알림 처리 시스템에 적합한 구조**입니다.

---

## 3. ⚡ 도입 전후 성능/안정성 비교

| 항목 | 도입 전 (단순 처리) | 도입 후 (Redis Streams) | 개선 효과 |
|------|----------------------|--------------------------|------------|
| TPS 처리량 | 약 300~400 | 700~1000 이상 | 🔼 2~3배 향상 |
| 메시지 유실 | 발생 가능 (예: 장애 중) | 없음 (재처리 로직 존재) | ✅ 보장 |
| 병렬성 | 없음 | ✅ 소비자 그룹 기반 병렬 처리 |
| 모니터링 | 미지원 | ✅ 처리 상태 추적 (PENDING 등) |
| 실패 메시지 처리 | 불가 | ✅ DLQ 구조로 재처리 가능 |

---

## 4. 🚀 기대 효과 및 확장 가능성

### ✅ 현재 효과
- ✅ **실시간 알림 처리 속도 및 안정성 향상**
- ✅ **Redis 기반의 낮은 지연성과 높은 가용성 확보**
- ✅ **메시지 유실 없는 아키텍처 구성**
- ✅ **장애 발생 시 미처리 메시지 재시도(XCLAIM) 가능**

### 🔧 향후 계획
- 🔄 DLQ 메시지에 대한 자동/스케줄 재처리 프로세스 도입
- 🔍 Redis 모니터링 도구 (Redis Insight 등) 연계
- 📊 Prometheus + Grafana 기반의 소비율 / 처리량 대시보드 구성
